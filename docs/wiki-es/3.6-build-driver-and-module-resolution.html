Conductor y resolución de módulos

El conductor es la pieza que une todo: lee el fuente, resuelve los módulos, sirve la biblioteca estándar, localiza el compilador de C del sistema, enlaza los runtimes nativos de interfaz e inteligencia artificial cuando hacen falta y compila. Vive en fuente/conductor/compilar.cpp y se declara en incluir/nooki/conductor/compilar.hpp.

La orden de compilar

La entrada es nooki::conductor::compilar(), que recibe una estructura Opciones y los gestores de diagnóstico, y va pasando por las fases.

Opciones y resultado

Opciones lleva la ruta del fuente, dónde dejar el binario, si se conserva el C intermedio (conservar_intermedios) y si hay que parar antes: en la verificación semántica (solo_verificar) o en la emisión de C (solo_c). Resultado devuelve el código de salida, el C generado como cadena y la ruta del binario final.

Esas dos paradas anticipadas son las que usan las pruebas y la herramienta de documentación: comprobar que un ejemplo verifica no necesita compilarlo entero, y ver el C generado es la forma más rápida de entender qué hace el generador con una construcción.

Los módulos y la biblioteca incrustada

Nooki lleva la biblioteca estándar dentro del propio binario. No hay archivos sueltos que copiar ni que puedan faltar: cuando un usar pide un módulo conocido, el conductor entrega directamente el texto incrustado al analizador.

La función fuente_biblioteca(modulo) guarda el fuente de cada módulo —resultado, textos, listas, matematicas, fechas, archivo, csv, redes, los de interfaz…— y devuelve la vista correspondiente. Todos están escritos en Nooki, salvo los runtimes de interfaz e IA, que son C y se emiten junto al programa solo cuando se usan.

std::string_view fuente_biblioteca(std::string_view modulo) {
    if (modulo == "resultado") {
        return R"(// Biblioteca estándar: el resultado de una operación que puede fallar.
publico enumeracion resultado {
    Ok(valor: entero)
    Error(mensaje: texto)
})";
    }
    // ...
}

El proyecto y sus dependencias

Un proyecto se describe con nooki.toml, que se lee con nooki::leer_manifiesto() y se representa con la estructura Manifiesto. El manifiesto declara el nombre y la versión del proyecto y sus dependencias locales, y el conductor las añade a las rutas de búsqueda de módulos.

La búsqueda va en este orden: junto al archivo que hace el usar, en biblioteca/, en las carpetas padre, en las dependencias del manifiesto y, por último, en la biblioteca estándar. Ese orden es el que hace que un módulo del proyecto pueda llamarse igual que uno de la biblioteca sin pisarla por accidente.

El compilador de C

El conductor busca cc, gcc, clang o MSVC —se puede forzar uno con la variable NOOKI_CC—, lanza la compilación del C generado y devuelve el binario. Si no encuentra compilador, el diagnóstico es NOK6001; si el compilador falla, NOK6002, con la salida del propio compilador de C para que el problema se pueda ver.
